# 原版机械革命控制中心安装包分析

## 结论

`D:\Files\CSharp\18.ControlCenter\ControlCenter_5.17.49.6_Mechrevo.exe` 是 Uniwill（同方）在 2023 年制作的机械革命控制中心安装包。它和 L-Mechrevo 依赖的 `GCUBridge`、`GCUService`、`ACPIDriverDll`、`UWACPIDriver` 属于同一套 GCU（厂商硬件控制服务）体系，但服务版本不同：原版包的 `GCUService` 带有 Uniwill 的有效签名，`GCUBridge` 未带有效签名；此前 L-Mechrevo 安装目录中的服务则为 AISTONE（服务提供方）签名版本。

这份包对从 G-Helper（华硕控制工具）适配很有帮助。原版 `GCUService` 的部分关键类型可以直接静态反编译，已经能够看到风扇信息如何读取；这与此前 L-Mechrevo 捆绑服务受混淆保护的情况不同。2026 年 10 月 23 日的本机只读连接也已读到性能模式、处理器温度和风扇占空比。

目前还没有进行真实模式切换或游戏负载测试。风扇占空比是控制值，不能证明风扇实际转动；安装包中的风扇表也不能只凭目录名直接套到本机。

## 包内组件

| 组件 | 版本或证据 | 用途 |
| --- | --- | --- |
| `GCUBridge.exe` | 1.0.1.10；原版提取文件未带有效签名 | 本机 MQTT（消息协议）服务端，监听端口 13688 |
| `GCUService.exe` | 1.0.2.70；有效签名为 Uniwill Technology Inc. | 处理风扇、性能、电源、灯效等硬件命令 |
| `ACPIDriverDll.dll` | 1.0.0.1；有效签名为 Uniwill Technology Inc. | 调用 ACPI/EC（嵌入式控制器）驱动 |
| `UWACPIDriver.sys` | `DriverVer=09/13/2022,17.53.43.609`（驱动日期与版本）；硬件标识为 `ACPI\INOU0000` | 内核层 EC 访问，服务名 `UWACPIDriver` |
| UWP 控制台 | `GamingCenter3_Cross.UWP_5.17.49.6_x64.msix` | 用户界面和托盘程序 |

原版 `GCUBridge` 的程序集元数据（程序结构信息）显示使用 `MQTTnet.Server`（MQTT 服务端库），创建 `MqttServer` 并调用 `ValidatingMqttClients`（客户端连接校验）。默认端口是 `13688`。

## 安装和卸载动作

从安装脚本静态提取到的动作包括：

1. 注册并启动 `GCUBridge` Windows 服务。
2. 解出并安装 `UWACPIDriver.inf`（驱动安装信息文件），硬件标识为 `ACPI\INOU0000`。
3. 预安装 UWP 包及其运行库，安装 WebView2（网页界面运行时）。
4. 写入 `HKLM\SOFTWARE\OEM\GamingCenter2`（控制中心配置注册表项）。

卸载动作会停止托盘进程、移除驱动设备、移除 UWP 包，并执行 `get-appxpackage *ControlCenter3* | remove-appxpackage -AllUsers`（查找并移除所有用户的控制中心应用）。这说明原版安装体系确实包含移除控制中心的动作，但不能仅凭这份脚本确定 L-Mechrevo 安装时具体执行了哪一步，也不能据此认定它是当时原版控制中心消失的直接原因。还需要那次安装日志或实际调用记录才能确认。

## 性能模式和风扇协议证据

UWP 主界面的 `GamingCenter3_Cross.dll` 和托盘程序的字符串、类型信息都出现了以下主题和字段：

- `Fan/Control`（风扇与模式控制）
- `Fan/Status`（风扇与模式状态）
- `Fan/Table`（风扇表）
- `System/FanInfo`、`System/FanErrorInfo`（风扇状态和故障状态）
- `CpuFanDuty`、`GpuFanDuty`（处理器/显卡风扇占空比）
- `OperatingMode`（当前运行模式）
- `OPERATING_GAMING_MODE`、`OPERATING_OFFICE_MODE`、`OPERATING_TURBO_MODE`、`OPERATING_CUSTOM_MODE`（均衡、安静、狂暴、自定义模式枚举）

这些主题与 L-Mechrevo 当前文档中的 GCU 消息主题一致，说明两者使用同一套协议体系。名称相同不代表各版本上报的字段完全相同；本机只读连接已经发现了以下差异。

### 本机只读实测

本机型号为 `Kuangshi16Pro Series GM6PX0X`（旷世 16 Pro），主板型号为 `GM6PX0X`，BIOS（固件）版本为 `N.1.09MRO07`。已安装原版服务文件的哈希与解包文件一致，连接目标为本机回环地址。原始记录保存在 `research\protocol-readonly-probe.json`（只读协议观察记录），该目录不纳入提交。

| 主题或信息 | 实际观察 | 适配含义 |
| --- | --- | --- |
| `Fan/Status`（风扇与模式状态） | `OperatingMode` 为字符串 `"0"`，没有 `IsAC` 字段 | 支持字符串形式的数字；外接电源状态另从系统读取 |
| `System/FanInfo`（风扇信息） | 只有 `CpuFanDuty: 49` 和 `GpuFanDuty: 49` | 显示为两个风扇的 49% 控制值，不能换算或假定为实际转速 |
| `System/CpuInfo`（处理器信息） | `CpuTemperature` 为字符串数值，如 `"59"` | 可读取处理器温度，逐字段记录更新时间 |
| `System/GpuInfo`（显卡信息） | 不同观察窗口中收到情况不同；本次约 15 秒窗口未收到 | 显示缺失或过期，不能补成零，也不能借处理器消息刷新显卡数据 |

模式值按当前协议对应为 `0 = Office`（安静）、`1 = Gaming`（均衡）、`2 = Turbo`（狂暴）。本次仅观察到服务上报的 `0`，没有主动切换其他模式。服务回报模式只能证明服务状态，不能单独证明功耗、风扇和固件都已按该模式运行。

### 原版风扇读取实现

原版 `GCUService 1.0.2.70` 中的 `MyControlCenter.FanInfo`（风扇信息类型）可以静态反编译。已看到的读取路径如下，地址均为十进制：

| 数据 | 反编译中看到的计算或地址 |
| --- | --- |
| 处理器风扇占空比 | EC（嵌入式控制器）地址 `1883`，读取值除以 `2` |
| 显卡风扇占空比 | EC 地址 `1884`，读取值除以 `2` |
| 处理器风扇实际转速 | EC 地址 `1124` 为高字节、`1125` 为低字节 |
| 显卡风扇实际转速 | EC 地址 `1132` 为高字节、`1131` 为低字节 |

这是该版本服务中存在的代码路径，并不表示每种机型都会使用这些地址，也不表示当前消息发布路径会调用所有读取函数。实测消息没有实际转速字段，所以当前适配没有直接访问这些寄存器，也没有用占空比推断转速。

## 风扇表和机型覆盖

安装包外置 `UserFanTables`（用户风扇表）包含 24 个 PH4/PH6 平台目录，共 144 个 JSON 文件。每个表通常有 `PL1`、`PL2`（持续/短时处理器功耗）、`TCC`（温度控制偏移）、CPU/GPU 各 16 个温度区间和占空比。

原版安装器内部还带 `DefaultFanTable_Gaming.json`、`DefaultFanTable_Office.json`、`DefaultFanTable_Turbo.json`（均衡、安静、狂暴默认风扇表）和 `M1T1` 至 `M4T5` 表。安装脚本只在机型检查通过时复制这些表。

PH4/PH6 是配置目录中的平台标识，GM6PX0X 是本机系统及主板型号，两者不一定直接对应。不能因为目录中没有 GM6PX0X 就断言包内没有适用风扇表；需要继续核对 `ProjectID`（项目标识）、安装条件和服务选择逻辑。本机注册表的 `BIOS_PROJECT_ID` 为 `IDX`，服务实测上报的 `FAN_TableName` 为 `M2T1`，这些线索尚不足以确认具体文件与本机固件的完整对应关系。当前适配不导入或重写任何风扇表。

## MQTT 认证（不记录凭据）

静态反编译显示，原版桥接服务对本机连接执行三项校验：

- 根据 `ClientId`（客户端标识）查找对应用户名。
- 根据用户名查找对应密码。
- 本机连接成功后才接受控制消息；非本机连接走另一套加密密码校验。

每类官方客户端由 `ClientManager(string ClientId, int AccountNumber)`（客户端管理器）生成 20 个账号槽位，并将客户端标识、用户名和密码放入内存字典。服务还分别为 UWP、键盘、托盘和插件保留客户端槽位。文档和源码不保存任何账号或密码。

当前适配默认连接 `127.0.0.1:13688`，仅对已审查、文件哈希匹配的原版 `GCUBridge.exe` 进行只读解析，通过 PE（可执行文件）元数据和方法指令在内存中构造认证信息，不加载或执行厂商程序集。实际账号、密码不写入源码、日志或研究文档。自动发现并连接本机原版后台已通过只读验证。

若文件版本未知、发现失败或认证失败，界面提示无法连接，保留显式配置连接信息的方式。不会因此自动改用直接 EC 访问，也不会猜测寄存器地址或停止原版服务。

## 证据范围和限制

以上结论来自安装器 PE（可执行文件）静态解包、`install_script.iss`（安装脚本）、UWP（Windows 应用平台）文件列表、程序集元数据及选定类型的静态反编译，以及本机文件版本、签名、哈希和只读消息观察。

研究过程中未运行厂商安装器、未加载厂商程序集、未修改服务或驱动。只读客户端订阅遥测并发送状态查询与遥测开启请求，没有发送模式切换、风扇表、功耗或 EC 写入命令。

原版服务仍是闭源软件，能够反编译不等于获得开源授权。当前已经掌握部分认证、消息和风扇读取实现，但还未完整追踪每个性能模式到硬件的执行路径，更未完成真实模式切换、实际风扇转速或游戏负载验证。现阶段不能宣称已经解决游戏中风扇不转的问题。

后续研究已经继续追踪模式写入、风扇表布局、电源变化和保护回退，结果见《绕过厂商后台的硬件与保护研究》。独立探针已用带读写权限的设备句柄执行只读请求，成功取得两路实际转速；读取控制码本身带有写访问标志，但探针没有发送 EC 写入。执行模式切换、EC 写入和负载测试仍未进行。
