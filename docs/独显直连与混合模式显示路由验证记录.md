# 独显直连与混合模式显示路由验证记录

日期：2026 年 10 月 24 日

状态：直连 → 混合 → 直连的双向切换已完成，当前恢复到独显直连。只读路由采集已接入探针，界面切换功能尚未实现。

## 结论

这台机器的显示模式只有两档：独显直连和混合模式，没有独立核显模式。

- 服务状态里的 `DiscreteGpuDirectConnectionSwitch_Status` 是目标值，不是当前已经生效的硬件路由。切换后、重启前，它会先改变，但内屏仍保持原来的接线。
- 实际路由需要同时读取两件事：内屏当前挂在 Intel／AMD 核显还是 NVIDIA 独显，以及 NVIDIA 独显是否正常在位。
- 已验证：`TOGGLE_ON` 对应目标独显直连；`TOGGLE_OFF` 对应目标混合模式。两个方向都必须重启后才真正生效。
- 当前厂商服务为 1.0.2.70，只使用 `DGPU_DIRECT_CONNECT_TOGGLE_ON/OFF`。本轮没有使用、也没有验证 `DGPU_DIRECT_CONNECT_RESTART`，实现时不应把它当成这版服务的可用能力。
- `DGpu=NV_CTRL_PANEL_AUTOSELECT` 在直连和混合两种状态下都没有变化，不能拿来判断 MUX（显示路由切换器）当前状态。
- 首次进入混合模式时，Windows 自动安装了 Intel 核显驱动。安装过程中显示布局被重新识别，用户观察到配置变乱；驱动完成后显示恢复。后续切换仍可能重建布局，但不应再次经历首次安装驱动这一过程。

最终核对结果：

| 项目 | 最终值 |
| --- | --- |
| 服务目标 | `DGPU_DIRECT_CONNECT_TOGGLE_ON` |
| 内屏实际适配器 | NVIDIA，`VEN_10DE` |
| 内屏输出 | `DISPLAYCONFIG_OUTPUT_TECHNOLOGY_DISPLAYPORT_EMBEDDED` |
| 内屏活动状态 | 活动 |
| NVIDIA 设备 | 在位，驱动已启动 |
| 实际显示路由 | 独显直连 |
| 服务支持位 | `Support` |
| 探针完整性 | 两轮复采均为完整遥测 |

## 数据口径

### 服务目标

服务中的两个关键字段：

| 字段 | 含义 |
| --- | --- |
| `DiscreteGpuDirectConnectionSwitch_Status` | 厂商服务已保存的显示目标 |
| `DiscreteGpuDirectConnectionSwitch_Support` | 服务是否支持该显示切换字段 |

本轮 `_Support` 始终为 `Support`。目标值只有两种：

| 目标值 | 目标模式 |
| --- | --- |
| `DGPU_DIRECT_CONNECT_TOGGLE_ON` | 独显直连 |
| `DGPU_DIRECT_CONNECT_TOGGLE_OFF` | 混合模式 |

本轮没有收到 `IGpuOnlyConnectionSwitch_Status` 或 `IGpuOnlyConnectionSwitch_Support`，与用户说明的“没有独立核显模式”一致。

### 实际硬件路由

探针使用两类只读信息：

1. 用 Windows DisplayConfig（显示配置接口）的 `QDC_ALL_PATHS`（全部显示路径）找到内屏目标。
2. 用 `GET_ADAPTER_NAME`（读取适配器名称）判断内屏连接的是 Intel／AMD 核显还是 NVIDIA 独显。
3. 用 Windows CfgMgr（设备配置管理器）确认 NVIDIA 显示设备是否在位、是否已启动。

路由推断：

| 内屏适配器 | NVIDIA 设备 | 实际路由 |
| --- | --- | --- |
| NVIDIA 独显 | 在位 | 独显直连 |
| Intel／AMD 核显 | 在位 | 混合模式 |
| Intel／AMD 核显 | 禁用或不存在 | 核显模式，但本机不提供这一目标 |
| 无法识别 | 任意 | 未知，不推断 |

这条路线不使用 NVML（NVIDIA 管理库）或 NVAPI（NVIDIA 应用接口）。两者可能唤醒独显或占用句柄，不适合在切换前做轻量路由回读。

### 为什么不用 `DGpu`

`Setting/Status.DGpu` 在两种实际路由下都是：

```text
NV_CTRL_PANEL_AUTOSELECT
```

因此它只能说明 NVIDIA 全局首选图形处理器相关配置，不能证明内屏当前接在哪块显卡上。

### 为什么没有使用 `GPUDevice/Status`

探针已订阅 `GPUDevice/#`，并在每次状态查询中请求 `Setting/Control GETSTATUS`，但本轮没有收到 `GPUDevice/Status`。该主题在本机主要承载刷新率等附加状态，不能作为本次 MUX 路由的替代证据。

## 服务字段结果

### 直连与混合的差异

| 字段 | 直连时 | 混合时 |
| --- | --- | --- |
| `DiscreteGpuDirectConnectionSwitch_Status` | `DGPU_DIRECT_CONNECT_TOGGLE_ON` | `DGPU_DIRECT_CONNECT_TOGGLE_OFF` |
| `DiscreteGpuDirectConnectionSwitch_Support` | `Support` | `Support` |
| `IGpuOnlyConnectionSwitch_Status` | 未收到 | 未收到 |
| `IGpuOnlyConnectionSwitch_Support` | 未收到 | 未收到 |
| `DGpu` | `NV_CTRL_PANEL_AUTOSELECT` | `NV_CTRL_PANEL_AUTOSELECT` |
| 实际内屏适配器 | NVIDIA | Intel |
| 实际路由 | 直连 | 混合 |

`Customize/SupportInfo`（能力支持信息）中的 `DGpuDirectConnectionSupport=1`，与 `Setting/Status` 的支持位一致。

### 目标与实际不一致是正常中间态

每次切换后，服务会先保存新目标，硬件要等下一次重启才改变。两个中间态都复现了这个顺序：

```text
直连 → 点击混合 → 服务目标 OFF / 实际仍为直连
直连 → 重启 → 服务目标 OFF / 实际为混合

混合 → 点击直连 → 服务目标 ON / 实际仍为混合
混合 → 重启 → 服务目标 ON / 实际为直连
```

因此，客户端收到的第一个新状态只能说明“目标已被服务接受”，不能显示“切换完成”。

## 屏幕布局与驱动变化

### 混合模式首次重启后

第一次重启到混合模式后，Windows 自动安装 Intel 核显驱动。驱动安装前，系统曾报告 3 个活动显示源：

| 显示源 | 主屏 | 桌面范围 |
| --- | --- | --- |
| `DISPLAY2` | 是 | `(0,0)`，2048×1152 |
| `DISPLAY3` | 否 | `(2048,-900)`，800×1280，竖屏 |
| `DISPLAY41` | 否 | `(4096,0)`，1707×1067 |

用户此时观察到屏幕配置变乱。该现象与内屏从 NVIDIA 路由改到 Intel 路由、驱动重新枚举显示目标相吻合。

### Intel 驱动完成后

驱动版本变为 31.0.101.5445。屏幕恢复后，系统报告 2 个活动显示源：

| 显示源 | 主屏 | 桌面范围 |
| --- | --- | --- |
| `DISPLAY2` | 是 | `(0,0)`，2048×1152 |
| `DISPLAY3` | 否 | `(2048,-900)`，800×1280，竖屏 |

混合模式下，内屏目标的适配器是 Intel，Windows 分配的源名称为 `DISPLAY42`，但该内部路径当时不是活动路径。这个结果与桌面上的两个活动显示源并不矛盾，也说明不能只凭显示源编号判断内屏。

### 最终直连

重启回直连后，活动显示源重新分配为：

| 显示源 | 主屏 | 桌面范围 |
| --- | --- | --- |
| `DISPLAY1` | 是 | `(0,0)`，2048×1152 |
| `DISPLAY2` | 否 | `(2048,-900)`，800×1280，竖屏 |

最终回读确认 `DISPLAY1` 是活动内屏，适配器为 NVIDIA。

显示源编号会随显示驱动和 MUX 状态变化，不能保存为长期标识。以后若要自动恢复布局，需要基于显示器硬件标识与适配器组合保存，而不是只记 `DISPLAY1/2`。

## 排查方式

### 1. 先读服务目标和能力

请求 `Setting/Control GETSTATUS`，检查：

- `DiscreteGpuDirectConnectionSwitch_Status`
- `DiscreteGpuDirectConnectionSwitch_Support`
- 是否意外出现 `IGpuOnlyConnectionSwitch_*`

如果能力位不是 `Support`，或目标值不认识，应显示“不支持／未确认”，不能猜测模式。

### 2. 再读实际硬件路由

读取内屏 target（显示目标）：

- 使用 `QDC_ALL_PATHS`，因为内屏未点亮时也可能不在活动路径中。
- 只接受内置、嵌入式 DisplayPort、LVDS、嵌入式 UDI 等内部输出类型。
- 读取 target 对应的 adapter device path。
- 路径含 `VEN_10DE` 判为 NVIDIA；含 `VEN_8086` 或 `VEN_1002` 判为核显。
- 同一内屏如果出现互相冲突的适配器，返回未知，不猜。

然后通过 CfgMgr 读 NVIDIA 显示设备：

- 存在且 `DN_STARTED`：在位。
- 存在但问题码 22：被禁用。
- 不存在：缺席。
- 读取失败或状态混合：未知。

### 3. 组合判断

只有下列组合才形成明确路由：

- 内屏 NVIDIA + 独显在位：直连。
- 内屏 Intel／AMD + 独显在位：混合。

任何一半未知，都不能把服务目标当成硬件事实。

### 4. 重启前后各读一次

一个完整的切换验证至少需要四点：

| 时间点 | 要验证什么 |
| --- | --- |
| 切换前 | 实际路由与当前目标一致 |
| 提交目标后 | 服务目标已变化，但实际路由保持不变 |
| 重启后 | 实际路由与目标一致 |
| 稳定后复采 | 驱动初始化完成后结果没有反转 |

### 5. 屏幕异常时检查驱动

如果切换后黑屏、分辨率异常或布局错乱：

1. 确认内屏适配器是否已经切换到另一块显卡。
2. 检查核显驱动是否安装完成。
3. 检查 Windows 当前活动显示源和桌面范围。
4. 等驱动安装结束后重新读取，不在驱动尚未就绪时立即判断切换失败。
5. 不自动修改分辨率、缩放或主屏，避免与正在进行的驱动安装竞争。

## 后续实现建议

### 状态模型

界面至少需要区分：

- 目标：直连。
- 目标：混合。
- 实际：直连。
- 实际：混合。
- 待重启：目标与实际不同。
- 未确认：服务或硬件回读缺失。

不能用单一布尔值把“目标”和“实际”合并。

### 提交切换

当前服务的可用动作是：

```text
Setting/Control
{"Action":"DGPU_DIRECT_CONNECT_TOGGLE_ON"}

Setting/Control
{"Action":"DGPU_DIRECT_CONNECT_TOGGLE_OFF"}
```

提交后：

1. 等待 `Setting/Status` 新帧。
2. 确认目标值变化。
3. 立即重新读取硬件路由。
4. 如果目标与实际仍不同，显示“待重启”。
5. 由用户自行安排重启，不在提交后自动重启。

当前记录没有证明 `DGPU_DIRECT_CONNECT_RESTART` 可用，因此不要发送该动作，也不要依赖厂商服务替用户重启。

### 重启后确认

启动后显示驱动可能还没有就绪，应延迟并重试实际路由读取。只有实际路由与目标一致时才显示“已生效”；未知时显示“未确认”；相反时显示“未生效”和实际路由。

### 显示器布局

切换 MUX 会改变内屏所使用的显卡，Windows 可能重建显示器拓扑。后续若自动恢复布局，应：

- 按显示器硬件标识和适配器分别保存。
- 在驱动初始化完成后恢复。
- 在布局未知、显示离线或外接屏路径冲突时停止恢复。
- 不与 MUX 切换、驱动安装或分辨率变更同时执行。
