# 自定义模式风扇曲线与究极进化只读验证记录

初次记录：2026 年 10 月 24 日；补充验证：2026 年 10 月 25 日。

状态：数据采集和单参数实测已闭环。用户在厂商控制台手动调整，YALM 采集服务、EC（嵌入式控制器）与实际转速；风扇增强由本轮 computer use（电脑操作通道）单参数切换并恢复。预设狂暴模式已做最终回读，Profile-2 的风扇增强也完成了开启和关闭对照。随后已把确认过的读取项和低风险写入项接入 YALM 的“风扇与功耗”页面，接入后的本轮真机检查仍只读。

2026 年 10 月 25 日补充：用户已通过 YALM（机械革命助手）分别应用第三套配置的处理器、显卡曲线。前后只读采集确认服务保存值和 EC（嵌入式控制器）曲线寄存器同步改变，详见“第三套曲线通过助手应用的真机验证”。此前各阶段仍保留 10 月 24 日的操作和观察范围，不能把两天的配置、保护状态或写入来源混为一轮。

## 结论

这轮验证的目的是确认自定义模式中的功耗、温度墙、风扇曲线、独立风扇输出和究极进化选项能否被服务回读，以及这些选项最终是否落到实际风扇行为。

- 自定义功耗、温度墙和风扇切换速度都能写入，并由 `Fan/Status` 与 EC（嵌入式控制器）寄存器同时回读到。
- 两路风扇曲线也确实写入了。曲线变化时，`Fan/Table.Activated` 会从 false（未激活）变为 true（已激活），EC 中两套 94 个曲线地址在首尾两次读取中完全一致。
- 界面勾选“开启风扇独立输出”后，退出控制台再采集，`FanControlRespective` 仍为 false（未启用独立控制）。该现象连续两轮出现，但本轮没有在控制台保持运行时做过并发采样，因此只能确认“退出后的服务回读为 false”，不能断言勾选后是否曾短暂生效。
- 两条差异很大的曲线仍然得到相同的 85% 双路控制值，没有观察到 CPU、GPU 各自按曲线分开调速。独立输出关闭、风扇安全保护触发或其他固件限制都可能造成这一结果，现有数据还不足以区分原因。
- 开启究极进化后，`OverClockingSwitch` 变为 1，相关选项在界面出现，自定义功耗、TCC（温度控制偏移）和风扇切换速度回到默认值，风扇表重新变为未激活并回到 M4T1 默认曲线。界面不再显示风扇曲线，但服务仍会发送完整的 `Fan/Table` 帧。
- 究极进化打开后并未自动启用具体超频：核心电压偏移、显卡核心频率偏移和显存频率偏移仍都是 0，内存超频开关仍为 0。
- 风扇安全位从测试开始就持续触发，直到究极进化采样结束仍未关闭。它早于所有曲线和独立控制改动出现，因此不能把本轮的曲线测试当成触发原因。
- Profile-2 的风扇增强可以正常切换。开启后服务 `FanBoostEnable=1`，EC 风扇模式 `0x0751` 从 0 变为 64，双路控制从 85% 升到 100%，实际转速增加约 700..770 转/分；关闭后全部恢复。
- 10 月 24 日结束时，用户的使用目标是预设狂暴模式；切回后已回读确认模式值 2、M3T1 默认表、130/130/200 W 和 95% 双路风扇控制。10 月 25 日用户另行进行了第三套自定义曲线验证，结果单独记录如下。

## 数据口径

### 采样方式

每个阶段使用 `--probe`（只读探针）采集 15 秒，约每 3 秒保存一个时间点。每个时间点包含：

- 最新服务状态帧。
- 两路 EC 风扇控制值和实际转速。
- 风扇安全位与通用热保护位。
- 16 个核心寄存器。
- 最新业务状态帧。

每个阶段还分别在开始和结束时读取 94 个风扇曲线寄存器，共两次。

### 完整性标记

顶层 `CompleteTelemetryReceived=true` 只表示至少有一个时间点同时收到了新鲜的服务状态、风扇状态和 EC 数据，不表示所有时间点都完整。

| 阶段 | 时间点 | 单点完整数 | 顶层完整标记 | 读取错误 |
| --- | ---: | ---: | --- | --- |
| A 基线 | 5 | 2 | true | 无 |
| B 功耗与温控 | 5 | 2 | true | 无 |
| C 前六槽调整 | 5 | 2 | true | 无 |
| D CPU 高、GPU 低 | 6 | 2 | true | 无 |
| E 究极进化 | 5 | 2 | true | 无 |
| F 切回狂暴 | 5 | 2 | true | 无 |
| G Profile-2 基线 | 5 | 2 | true | 无 |
| H Profile-2 风扇增强开 | 5 | 0 | false | 无 |
| I Profile-2 风扇增强关 | 5 | 0 | false | 无 |

首轮时间点常见服务温度或控制值尚未新鲜，因此单点 `Complete=false`。其他不完整时间点仍收到了曲线、寄存器和关键服务字段，但不能把整个阶段描述成“所有字段每秒都完整”。

### 数值换算

- EC 寄存器 `0x075B`、`0x075C` 是两路风扇控制原始值，单位 0.5%。170 对应 85%，190 对应 95%。
- `0x0786` 的 TCC（温度控制偏移）最高位表示启用，低 7 位是偏移量。目标温度 93 ℃、TjMax（结温上限）按 100 ℃ 计算时，偏移为 7；启用后原始值为 `0x80 + 7 = 135`。
- `0x0787` 的风扇切换速度以 100 ms 为一个原始单位，最高位表示启用。500 ms 对应 5 个原始单位；启用后原始值为 `0x80 + 5 = 133`。
- 风扇安全位取 `0x07A5` 的 bit 3。本次原始值始终为 8，即持续触发。
- 通用热保护取 `0x07C8` 的 bit 4。本次原始值始终为 `0x20`，bit 4 未触发。

时间：16:40:23..16:40:37。

服务处于自定义 Profile-1。长时、短时和瞬时功耗分别为 75、75、200 W；TCC 关闭；动态升压 25 W；风扇切换速度配置为 300 ms，但启用位为 0。风扇表 M4T1 处于未激活状态。

| 风扇强冷 | 关闭 |

### B：调整功耗、TCC 和风扇切换速度

时间：16:44:33..16:44:47。

用户把长时、短时和瞬时功耗改为 80、80、194 W；启用 93 ℃ CPU 温度墙；动态升压改为 22 W；启用 500 ms 风扇切换速度。显卡功耗目标仍为 125 W。核心与显存偏移仍为 0。

服务回读结果与界面一致：

- `CPU_TccOffset=7`，`CPU_TccOffsetSwitch=1`。
- `0x0786=135`，表示启用位加 7。
- `FAN_FanSwitchSpeed=500`，`FAN_FanSwitchSpeedEnabled=1`。
- `0x0787=133`，表示启用位加 5 个 100 ms 单位。
- `0x0783..0x0785=80/80/194`。

实际风扇行为没有随功耗参数的这组变化发生明显改变：处理器 91 ℃、显卡 51 ℃，双路仍为 85%，处理器风扇 4791..4834 转/分，显卡风扇 4688 转/分。风扇表仍未激活，安全位仍触发，通用热保护未触发。

### C：勾选独立输出并压低 CPU 前段、拉高 GPU 前段

时间：16:50:00..16:50:15。

用户修改了两路曲线，界面显示“开启风扇独立输出”已勾选。服务回读显示：

- `Fan/Table.Activated=true`，说明自定义表已经激活。
- `FanControlRespective=false`，独立输出仍为关闭。
- 功耗、TCC、动态升压和风扇切换速度保持 B 阶段的值。

按固定 0 的 ID0 之后六个可拖动点计算：

| 曲线 | ID1..6 回读值 |
| --- | --- |
| CPU | 0、1、1、1、1、66% |
| GPU | 34、42、52、60、67、68% |

这些值是实际保存结果。它们只能说明固件接受了这些边界附近的值，不能直接当成通用“最小值/最大值”规格：

- ID0 两路都固定为 0%。
- CPU 拉到最低时，ID1 为 0%，ID2..5 回读为 1%。
- GPU 拉到最高时，ID1..6 得到 34、42、52、60、67、68%，没有全部变成 100%。

实际行为没有出现独立调速：处理器 91..92 ℃、显卡 51 ℃，双路仍都是 85%，处理器风扇 4791..4834 转/分，显卡风扇 4688 转/分。安全位仍触发，通用热保护未触发。

### D：CPU 拉高、GPU 拉低并检查曲线尾部

时间：16:52:56..16:53:11。

自定义表仍为激活状态，独立输出仍回读为 false。有效曲线共有 ID0..10 共 11 个点，ID11..15 的 `UpT`、`DownT` 均为 255，作为尾值保留。

| --- | ---: | ---: | ---: | ---: |
| CPU | 88% | 95% | 100% | 100% |
| GPU | 62% | 62% | 62% | 62% |

实际结果仍为双路 85%。处理器为 87..90 ℃、显卡为 52 ℃，处理器风扇稳定在 4802 转/分，显卡风扇稳定在 4688 转/分。这个阶段进一步说明，仅凭两条曲线已保存并不能证明独立控制已经生效。

## 风扇独立输出

阶段 C 和 D 的界面截图都显示“开启风扇独立输出”处于勾选状态，但退出控制台后的服务回读都为：

```text
Fan/Table.Activated = true
Fan/Table.FanControlRespective = false
```

用户随后也确认，重新打开控制台时发现独立输出被关掉。该问题连续出现两次，但本轮没有保存“勾选瞬间”的服务帧，因此能确认的事实是：

1. 曲线和 `Activated=true` 能保留。
2. 退出控制台后，独立输出回读为 false。
3. 两条曲线的明显差异没有反映到实际双路控制值上。

不能仅凭这三项就确定是“退出时被重置”还是“服务从未接受该开关”。后续若实现该功能，应在勾选后、退出前、退出后各取一帧，并记录 `SwitchFanRespective` 请求的确认结果。

本轮原始数据给出的边界是：

- 安全位在开始调整曲线前就已经触发。
- 自定义风扇控制值从 85% 升到 95% 后，安全位仍未恢复。
- 通用热保护位始终没有触发。
- 处理器一直在 87..93 ℃，后台负载没有降低，无法区分高负载、固件保护策略、独立风扇状态或控制台提示之间的因果关系。

原版控制台底部出现过 `Fan Safety Protect!`（风扇安全保护）提示，并说明当前风扇表没有恢复。提示里的 OK（确定）是灰的，用户尝试后也无法关闭；随后选择不再处理这个提示继续采样。现有证据只能记录这个现象，不能把它当作某个参数已被禁用的唯一原因。

历史测试里，负载降低后安全位曾自行恢复；本轮没有做降载后的恢复对照，因此本轮数据不能判断它的清除条件。

当前 YALM 面板把风扇安全位触发和“两路实际转速不够新鲜”一起作为禁用模式按钮的条件。最终 F 阶段已经在正常预设狂暴模式下稳定回读到安全位触发，同时两路风扇为 95% 且在 5195 转/分以上。继续沿用现在的判断，会把预设模式切换也一并锁住。后续逻辑建议把安全位当作醒目警告：

- 仍允许在办公、均衡和狂暴之间切换。
- 在安全位触发时停止新的自定义功耗、曲线和超频写入。
- 只有转速不可信、风扇错误位触发或通用热保护触发时，才禁用高风险写入并给出明确原因。

## 究极进化与超频字段

究极进化开关打开后，`Customize/SupportInfo`（能力支持信息）仍显示：

- `FanSettingsSupport=1`
- `OcSettingsSupport=1`
- `RamFan1p5Support=1`
- `FanBoostBtnSupport=0`

因此本机支持风扇设置和超频设置，但不支持界面上单独的风扇强冷按钮。风扇强冷的 EC 位或服务字段仍存在，后续实现不能只依据某一个能力位。

`OverClockingSwitch=1` 只证明了究极进化入口被打开。本轮没有输入任何非零偏移，也没有启用内存超频，所以没有验证：

- 核心电压偏移修改后是否在重启后生效。
- 显卡核心或显存频率偏移是否真正写入 NVIDIA 驱动。
- 内存超频开关是否只解锁 BIOS 选项。
- 超频后能否稳定运行。

### Windows 电源模式覆盖层

这里容易把三个不同的设置混在一起：

| 名称 | Windows 中的位置 | 作用 |
| --- | --- | --- |
| 电源计划 | 经典电源计划和高级电源设置 | 决定整套电源策略，例如平衡、高性能计划 GUID |
| 电源模式覆盖层 | 设置 → 系统 → 电源和电池 → 电源模式 | 在当前电源计划上覆盖调度倾向，只有最佳能效、平衡、最佳性能三档 |
| 处理器睿频 | 高级电源设置中的处理器性能提升模式 | 单独控制 CPU Boost 策略 |

G-Helper（华硕控制工具）在切换性能模式时会读取或使用覆盖层：

- 最佳能效使用 `961cc777-2547-4f9d-8174-7d86181b8a7a`。
- 平衡使用全零 GUID。
- 最佳性能使用 `ded574b5-45a0-4f42-8737-46345c09c238`。
- 写入接口是 `PowerSetActiveOverlayScheme`（设置活动电源模式覆盖层）。
- G-Helper 默认把安静映射到最佳能效、均衡映射到平衡、狂暴映射到最佳性能；如果启用了 `skip_powermode`，这部分会跳过。
- 电池节能模式开启时，Windows 可能忽略或覆盖这层选择。

它不会修改 EC（嵌入式控制器）中的功耗墙、风扇表或 TGP，也不会修改厂商服务里的模式值。处理器睿频是另一项设置，启用覆盖层不会自动替用户设定睿频。

本项目可以选择不做这一层，这不会影响读取厂商模式、功耗和风扇。但如果不实现，就不应在模式切换时调用 `PowerSetActiveOverlayScheme`，也不应把“模式切换完成”解释成 Windows 电源模式已经同步。G-Helper 的完整模式复制确实包含这部分，但可以作为一个独立开关后置。

实现时建议先完成只读面板和模式切换，再按下面的门槛逐项开放写入：

1. 先实现读取和界面，不在拖动曲线时自动写入。
2. 每次只写一个开关、一个数值或一条曲线。
3. 开关必须排在同组数值之前。
4. 服务回读、EC 寄存器或实际转速中，至少要有两类一致证据。
5. 独立输出、TGP、GPU 驱动偏移和究极进化在补足确认前保持只读或隐藏。
6. 写入失败、回读超时或安全位异常时，立即停止后续步骤，不继续提交整组参数。

## 排查方式

后续如果继续排查同类问题，可以按下面的顺序做。

### 1. 先确认控制台是否退出

关闭主窗口不一定等于退出托盘服务。本轮按用户要求在托盘菜单选择“退出”，然后运行探针。若控制台正在运行，先确认它是否允许并发连接；不要只凭主窗口消失就认定后台已经停止。

### 2. 运行只读探针

使用：

```powershell
D:\Files\CSharp\YALM\app\bin\x64\Release\net10.0-windows\YALM.exe --probe <绝对输出路径>.json 15
```

探针不会发送模式、功耗、曲线或 EC（嵌入式控制器）写入命令。

### 3. 检查连接和完整性

优先查看：

- `ConnectionDiscovered`
- `Error`
- `CompleteTelemetryReceived`
- 每个时间点的 `Complete`

如果连接阶段出现 `SocketException`（套接字异常），先检查 13688 端口和沙箱／权限限制。本轮在受限自动化环境中曾遇到“端口已监听，但沙箱内连接被拒绝”的情况；把同一个只读探针放到沙箱外运行后成功。这类失败不能当作硬件参数没有写入。

### 4. 服务与 EC 分开核对

同一个参数至少同时检查：

- `Fan/Status` 的服务回读值。
- `0x0783..0x0787` 等核心寄存器。
- 两路实际控制值与转速。

只看界面勾选或只看某一项服务字段都不够。本轮“独立输出界面已勾选、服务回读 false、实际风扇不分开”的差异就是例子。

### 5. 曲线要核对激活状态和完整表

风扇曲线需要同时检查：

- `Fan/Table.Activated`
- `Fan/Table.FanControlRespective`
- CPU/GPU 每条曲线的 16 个占空比。
- 首尾两次 94 地址曲线快照是否一致。

不能只用 `0x07C6` 或某一张图表判断曲线已经生效。

### 6. 保护位单独记录

风扇安全位和通用热保护位不是同一个字段。至少记录服务布尔值、`0x07A5`、`0x07C8` 和当时温度，避免把“安全位触发”误写成“通用热保护触发”。

### 7. 修改后恢复

每次只改变一组参数后，先保存并退出控制台，再运行探针。确认服务、寄存器、实际转速和保护位，再决定是否继续。本次切回狂暴模式后已经用 F 阶段完成最终回读。
